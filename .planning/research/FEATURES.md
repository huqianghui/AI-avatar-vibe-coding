# Feature Research

**Domain:** UI component library adapter migration (shadcn/Radix → Fluent UI v9)
**Milestone:** v3.0 Fluent UI v9 Migration (supersedes the v2.0 Avatar-MVP feature research previously in this file)
**Researched:** 2026-08-06
**Confidence:** HIGH (Fluent v9 API surface verified against `@fluentui/react-components` v9 published `.d.ts` files and source `.types.ts` files via WebFetch; current codebase read directly)

This is a component-mapping deliverable rather than a market-feature landscape (per the FEATURES template guidance, adapted for a technical migration). Sections retain the template shape but content is the per-component Radix→Fluent mapping table plus dependency/rollout ordering that feeds Phase 39/40 plan-phase.

## Feature Landscape (= Component Migration Landscape)

### Table Stakes (Must Preserve — Non-Negotiable for Adapter Mode)

| Requirement | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| All 21 migrated exports keep identical name + props signature | 126 consumer files must compile unchanged | HIGH (aggregate) | Verified via `index.ts` barrel — every export listed below must survive |
| `data-slot="xxx"` attribute preserved on every component | ~39 test assertions select via `[data-slot=...]` | MEDIUM | Simple to add manually to Fluent output; not automatic |
| `asChild` prop behavior preserved (33 files) | Consumers pass custom trigger elements (e.g. `<Link>` as Button) | HIGH | Fluent has no `Slot`/`asChild` concept — needs manual `cloneElement` shim per component |
| Checkbox/Switch consumer call sites unchanged (`onCheckedChange`, boolean) | Existing forms bind `onCheckedChange={(v) => ...}` expecting a bare boolean | HIGH | Fluent native signature is `onChange(ev, data)` where `data.checked` — adapter must translate |
| `toast.loading()` + `toast.dismiss(id)` semantics | `avatar-page.tsx:224-243` depends on this | HIGH | Handled in Phase E, not B/C, but documented here since it's part of ecosystem parity |
| `SheetContent side="bottom"` visual behavior | 1 call site (`avatar-page.tsx:446`) | MEDIUM | Fluent Drawer **does** support `position="bottom"` (see mapping row C2 — the migration plan's assumption that Fluent has no bottom is incorrect) |
| Radix `data-state` test assertions | `checkbox.test.tsx:20,26` asserts `toHaveAttribute("data-state", "checked"/"unchecked")`; similar patterns likely exist informally in dropdown-menu/select/sheet/tooltip visual states even where not yet in dedicated test files | HIGH | Fluent does **not** emit `data-state` — must rewrite to `aria-checked`/`aria-selected`/`aria-expanded` equivalents, or have the adapter itself re-emit `data-state` manually to avoid touching passing tests (see mapping table) |

### Differentiators (Value of Migration)

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Visual parity with Azure AI Foundry portal | Client-facing consistency with Azure ecosystem | MEDIUM | Achieved via Griffel theme bridge (Phase A), not component API — out of scope for this doc |
| Griffel `makeStyles` replaces ad-hoc Tailwind variant strings | More maintainable variant logic, easier to keep in sync with Fluent theme tokens | MEDIUM | Applies per-component during Phase B/C |
| Native a11y improvements (Fluent components follow WAI-ARIA authoring practices out of the box) | Fewer manual `aria-*` props needed on composites like Menu/Combobox/Dialog | LOW | Side benefit, not a task itself |

### Anti-Features (Explicitly Avoid During This Migration)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|------------------|-------------|
| Migrating `scroll-area` to Fluent | Consistency completionism | User explicitly decided (2026-08-05) to keep custom Radix scrollbar visuals; Fluent has no native custom-scrollbar primitive matching current UX | Leave `scroll-area.tsx` untouched, keep `@radix-ui/react-scroll-area` dependency after Phase F cleanup |
| Big-bang rewrite of all 21 components in one commit | Faster on paper | Violates CLAUDE.md "逐个实现" rule; breaks bisectability/rollback | One component = one commit (already locked in plan) |
| Auto-scripting the 84 lucide→Fluent icon mapping | Speed | Fluent icon names don't 1:1 match lucide semantically (regular vs filled variants, missing icons) — plan already flags "不用脚本瞎猜" | Manual mapping table (Phase D, out of scope here) |
| Replacing `asChild` with a hand-rolled polymorphic `Slot`-style component | Looks idiomatic | Fluent v9 has no Slot/asChild concept at all; recreating one for parity adds complexity for no ecosystem gain | Minimal `React.cloneElement` shim inside each adapter that needs it (Button, Badge, DialogTrigger, SheetTrigger/DrawerTrigger, DropdownMenuTrigger/MenuTrigger, TooltipTrigger, FormControl) |

## Feature Dependencies

```
[Phase A: FluentProvider + theme bridge]
    └──requires──> nothing new (infra only)

[Phase B: 12 leaf components]
    └──requires──> [Phase A]   (FluentProvider must wrap the app before any Fluent component renders)

[C1 Dialog] ──de-risks──> [C2 Sheet]
    (both are built on modal/portal-family primitives — react-dialog vs react-drawer are
     separate Fluent packages, but landing Dialog's DialogSurface/backdrop-shim/portal-target
     learnings first reduces Sheet's risk even though they aren't code-dependent)

[C3 Select] ──independent of──> [C4 DropdownMenu]
    (different Fluent packages: react-combobox vs react-menu; no shared adapter code,
     but both are the two highest-complexity composites — sequence for team bandwidth/risk
     isolation, not because of a real code dependency)

[C5 Tabs] ──requires──> nothing from B/C directly (self-contained; benefits informally
    from the Button/Divider adapter patterns already established in Phase B)

[C6 Tooltip] ──composes with──> [Button (Phase B), DropdownMenuTrigger/MenuTrigger (C4)]
    (Tooltip commonly wraps icon-only Buttons and menu triggers in the admin UI — verify
     nested cloneElement-based triggers still forward refs correctly once Button's own
     asChild shim is live)

[C8b Form] ──requires──> [Label (Phase B)] shipped first
    (FormLabel's internal Label swap is meaningless until Label itself has already changed)

[Icon adapter (Phase D)] ──independent of── [Phase B/C]
    (icons only touch `[&_svg]` Tailwind selectors already present in each component's
     className; safe to sequence after B/C per the plan, no hard blocking dependency
     either direction)

[Toast bridge (Phase E)] ──independent of── [Phase B/C]
    (sonner.tsx is not one of the 21 in-scope B/C components; safe to defer)
```

### Dependency Notes

- **C1 Dialog before C2 Sheet:** not a hard code dependency (different Fluent packages), but both wrap modal/portal-family primitives with similar focus-trap and portal-target risk profiles — landing Dialog first de-risks Sheet's C2 work.
- **C3 Select and C4 DropdownMenu share no code** but are the two hardest composites by API-shape delta and both currently lack test coverage — plan-phase should treat these as the two most likely candidates for a dedicated spike/extra time budget, and should NOT bundle them into the same commit/session (risk isolation, per the plan's own "each component = independent commit" rule).
- **C8a Card is a decision point, not a dependency** — flag explicitly to plan-phase whether to adopt real Fluent `Card` (with its selectable-list semantics) or keep the current plain-div implementation with only Griffel token-color updates. Low cost either way; called out here so it isn't silently treated as "just like the other 8 composites."
- **C6 Tooltip composes with Button/MenuTrigger:** icon-button-wrapped-in-Tooltip (sometimes itself inside a MenuTrigger) is a recurring admin-UI pattern — verify the nested `cloneElement` shims (Button's `asChild` + Tooltip's implicit trigger children) don't double-clone or drop ref forwarding once both are migrated.
