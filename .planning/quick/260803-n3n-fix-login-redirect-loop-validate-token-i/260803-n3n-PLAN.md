<objective>
Fix the login redirect loop: `GuestRoute` (frontend/src/router/auth-guard.tsx) currently redirects away from `/login` based solely on token *existence* in the auth store, not token *validity*. A stale/expired token in localStorage therefore bounces the user straight back to `/` (or `/admin/dashboard`) with no way to reach the login form to re-authenticate. It also mis-routes on the very first render because `user` is `null` immediately after a page reload (before `/me` resolves), so even a valid admin token can momentarily route to `/` instead of `/admin/dashboard`.

Purpose: Restore the ability to log in after a token goes stale, and make the guest-route redirect decision reflect the user's *actual* resolved identity rather than a race-prone snapshot.

Output: `GuestRoute` validates the token via `useMe()` before redirecting (loading state while pending, stays on `/login` on failure since `clearAuth()` fires, redirects by real role on success). Unit tests cover all three states. A Playwright E2E test proves the real-world story: stale token in localStorage -> visit `/login` -> can still log in.
</objective>

From frontend/src/hooks/use-auth.ts (useMe -- already fetches /auth/me, self-heals on failure):
```typescript
export function useMe() {
  const { token, setAuth, clearAuth } = useAuthStore();
  return useQuery({
    queryKey: ["auth", "me"],
    queryFn: async () => {
      try {
        const res = await apiClient.get<User>("/auth/me");
        if (token) setAuth(token, res.data);
        return res.data;
      } catch {
        clearAuth(); // <-- on 401/any failure, token+user are cleared synchronously here
        throw new Error("Failed to fetch user");
      }
    },
    enabled: !!token, // query is a no-op when there is no token at all
    retry: false,
  });
}
```
