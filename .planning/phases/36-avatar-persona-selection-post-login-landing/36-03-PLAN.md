<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous client -> `/public/avatar/webrtc/session`, `/public/avatar/chat` | Untrusted, no JWT, may supply `persona_id` |
| authenticated user -> `/avatar/chat` (personalized) | Trusted identity via JWT, no client-supplied persona_id (server resolves from that user's own preference row) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-10 | Tampering | `webrtc/session` `persona_id` param | mitigate | `resolve_active_persona` enforces an enabled-only whitelist; invalid/disabled ids fall back to default silently — no error that would confirm an id's existence or enabled state |
| T-36-11 | Information Disclosure | disabled persona's `prompt_fragment`/greeting | mitigate | Same whitelist check as T-36-10 prevents a disabled persona's content from ever reaching a session |
| T-36-12 | Information Disclosure | `prompt_fragment` free-text field | mitigate | Two-gate sanitization: `sanitize_free_text_with_pii` at admin save time (Task 1) and again at chat-injection time (Task 3) |
| T-36-13 | Tampering | personalized chat persona resolution | mitigate | `resolve_active_persona` for the personalized path only ever reads `UserPreference` filtered by the JWT-authenticated caller's own `user_id` — never accepts a client-supplied user_id |
| T-36-14 | Denial of Service | oversized `prompt_fragment` inflating LLM context/cost | accept | Bounded by `sanitize_free_text_with_pii`'s existing `max_length=2000` cap, reused unchanged |
</threat_model>
