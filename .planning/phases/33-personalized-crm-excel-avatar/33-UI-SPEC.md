# Phase 33 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Source note:** This phase inherits the design-system decision, spacing scale, typography, and color tokens locked in `32-UI-SPEC.md` (approved, same app, adjacent avatar surface) rather than re-deriving them from scratch — Phase 33 adds three new UI surfaces (Admin "CRM 数据" page, Admin user "个性化" section, avatar-page personalization badge) on top of the already-approved Phase 32 avatar shell. Deviations from Phase 32's contract are called out explicitly where they occur.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no `components.json` / shadcn CLI in this repo (verified: `ls frontend/components.json` → not found). Same decision as Phase 32: this project uses a hand-built Radix wrapper library seeded from a Figma Make design system (Phase 01/01.1/10). **Do not run shadcn init for this phase either** — it would fragment an already-established, 32-phase-validated component set. |
| Preset | not applicable |

| Font | `--font-sans: 'Inter', 'Noto Sans SC', sans-serif` (`frontend/src/styles/index.css` `@theme inline`) — no new font needed |

**Registry Safety Gate: not applicable** — shadcn not initialized. All new UI (admin CRM-data page, user-personalization section, avatar-page badge) is composed exclusively from the existing `ui/*` primitives.

## Spacing Scale

Declared values (must be multiples of 4), inherited from the project's Tailwind v4 scale (same as Phase 32):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside preference-tag chips, badge padding |
| sm | 8px | Gap between preference-tag chips (`gap-2`), gap between import-result summary badges |
| md | 16px | Default card padding (`CardContent`, personalization-section padding), gap between form fields in the tag-add row |
| lg | 24px | Page-level `space-y-6` rhythm on the CRM-data admin page (matches `training-materials.tsx`/`settings.tsx`), dialog padding |
| xl | 32px | Empty-state vertical padding (`py-8`) inside the "no import yet" state and the "no preference tags yet" state |
| 2xl | 48px | (reserved — not used by this phase's new components) |
| 3xl | 64px | (reserved — not used by this phase's new components) |

Exceptions: none. This phase introduces no icon-only custom touch targets — all new interactive elements (upload button, download-template link, tag add/edit/delete, badge) reuse the existing `Button`/`Badge` component's built-in sizing (`size="icon"` = 36px, `size="sm"` = 32px), consistent with every other admin page in the codebase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 (regular) | 1.5 |
| Label | 14px | 400 (regular) | 1.4 |
| Heading | 20px | 600 (semibold) | 1.3 |
| Display | 24px | 600 (semibold) | 1.2 |

Exactly 2 weights across all four roles — **400 regular** (Body, Label) and **600 semibold** (Heading, Display) — identical contract to Phase 32, for visual consistency across the avatar/admin surfaces.

**Implementation note (inherited from Phase 32):** override the global `button { font-weight: 500 }` base rule with explicit `font-normal`/`font-semibold` utilities on any new custom text inside the tag chips, badges, and result-summary text, to stay within the 2-weight contract.

**Usage map (Phase 33 additions):**
- Body (16/400): CRM import-result summary sentence ("成功导入 N 行，跳过 M 行"), personalization-section body copy, preference-tag value text
- Label (14/400): table column headers, skipped/unmatched reason text, "专属模式" badge label, preference-tag category text, helper/hint text under the upload dropzone
- Heading (20/600): "CRM 数据" page section-card titles ("上传 CRM 映射表", "上次导入结果"), "个性化" dialog title
- Display (24/600): page `<h1>` on the CRM-data admin page ("CRM 数据"), matching `text-2xl font-medium` `h1` pattern already used by `training-materials.tsx`/`users.tsx` (note: existing pages use Tailwind's default `font-medium`=500 for their `h1`; per the 2-weight contract, this phase's new `h1` MUST use `font-semibold`, matching Phase 32's Display role — flag this as a **minor deviation from the existing admin `h1` convention**, intentional for the declared 2-weight contract, not an inconsistency to "fix" on other pages)

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (#FFFFFF) | Page canvas, dialog surfaces, card backgrounds (`--card` also #FFFFFF) |
| Secondary (30%) | `--muted` (#F9FAFB) + `--card` + `--border` | Table header rows (`bg-muted/50`), personalization read-only card background, dropzone default background, card borders |
| Accent (10%) | `--primary` (#1E40AF) | **Reserved for exactly these 5 elements — nothing else:** (1) "上传 CRM 数据" primary upload button, (2) "下载模板" download-template action (ghost button, `text-primary`), (3) "专属模式" badge (`bg-primary/10 text-primary border-primary/20`), (4) preference-tag "添加" (add) button, (5) success-count figure in the import-result summary (`text-primary` on the N in "成功导入 N 行") |
| Warning (semantic, not new — reuses existing `--weakness` #F97316 token) | `--weakness` | Skipped-row count and unmatched-row count in the import-result summary, plus their expandable detail-row backgrounds (`bg-weakness/10`) — these are **not errors**, just informational counts per D-04's "跳过并报告" (skip-and-report) behavior; must render in the existing orange/warning tone, never destructive red |
| Destructive | `--destructive` (#EF4444) | **Reserved for exactly these 2 elements:** (1) header-validation-failure banner (the whole-file-rejected 400 case), (2) preference-tag delete confirmation button. Never used for skipped/unmatched rows (those are `--weakness`, see above) — a partial import is expected, successful behavior per D-04, not an error state. |

Accent reserved for: upload button, download-template link, "专属模式" badge, tag-add button, success-count figure. **Never** apply `--primary` to the skipped/unmatched counts, table header text, or any other passive/informational element.

## Layout Contract

### 1. Admin "CRM 数据" page (D-12) — new page, sibling to Settings/Training Materials in the admin nav

**Structural reference:** `training-materials.tsx`'s dropzone-upload pattern + `settings.tsx`'s `Card`-sectioned page layout (both inspected — no existing sibling page for `PublicKnowledgeConfig` to copy per RESEARCH.md finding; these two are the actual structural donors).

```
┌─────────────────────────────────────────────────┐
│ CRM 数据                                    (h1) │
│ 上传 Excel CRM 映射表，管理用户个性化上下文数据    │ (Body, muted)
├─────────────────────────────────────────────────┤
│ Card: 上传 CRM 映射表                             │
│  [Dropzone: 拖拽或点击上传 .xlsx 文件]             │
│  [下载标准模板]  (ghost button, text-primary)     │
│  [上传] (primary button, disabled until file set)│
├─────────────────────────────────────────────────┤
│ Card: 上次导入结果                                 │
│  成功导入 12 行 · 跳过 2 行 · 未匹配 1 行           │ (summary line)
│  ▸ 跳过详情 (expandable, weakness tone)            │
│  ▸ 未匹配详情 (expandable, weakness tone)          │
└─────────────────────────────────────────────────┘
```

- Page container: `space-y-6`, identical rhythm to every other admin page.
- Upload card: reuse `useDropzone` exactly as in `training-materials.tsx` but restricted to `.xlsx` only (`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`), single file, max size mirrored from `MAX_MATERIAL_FILE_SIZE` (4MB) per RESEARCH.md's DoS mitigation note.
- "下载模板" is a plain ghost `Button` (or `<a>` styled as one) triggering a `GET /admin/crm/template` download — no dialog, no confirmation (non-destructive).
- Import-result card: on 200 (partial or full success), render three summary badges (`Badge` component): success count (`bg-primary/10 text-primary`), skipped count (`bg-weakness/10 text-weakness`), unmatched count (`bg-weakness/10 text-weakness`) — followed by two independently expandable detail lists (reuse the `ScrollArea` + row-list pattern from `training-materials.tsx`'s "Version History Dialog" body, but inline on the page, not in a dialog) showing `email — reason` per skipped/unmatched row.
- On 400 (header mismatch): render a single destructive inline alert banner above the dropzone — **do not** show the result-summary card at all in this case (whole file rejected, no partial data exists).

### 2. Admin Users page — "个性化" section (D-11) — extends existing `users.tsx`, does NOT create a new standalone page

**Structural reference:** `users.tsx`'s existing `DropdownMenu` action pattern (currently: 激活/停用, 删除) + `training-materials.tsx`'s `Dialog` edit pattern.

- Add a third `DropdownMenuItem` to each user row's action menu: "个性化" (icon: `UserCog` from lucide-react), opening a new `Dialog` (`sm:max-w-lg`, matching the Edit Dialog width convention).
- Dialog body, stacked in `space-y-4`:
  1. **CRM match status** (read-only `Card`, `bg-muted` background, no border-primary — this is informational, not an accent element): a status row showing either — matched: green dot (`bg-strength`) + "已匹配 CRM 数据" + `customer_name` + `company` (Body 16/400) — **never** render `crm_notes` or `contact_person` in this summary view (minimize exposure of free-text CRM content in a UI surface that isn't the dedicated CRM-data page); or unmatched: muted dot (`bg-muted-foreground`) + "未匹配 CRM 数据" (Label 14/400, muted-foreground) — **neutral tone, not destructive/warning** (an unmatched user is expected, not an error, per D-08's "silent" framing extended to this admin view).
  2. **偏好标签** (preference tags) section: a `Badge`-chip list (`variant="secondary"`, `gap-2` wrap layout) — each chip renders `{category}: {value}` (Label 14/400) with a trailing inline `X` icon-button (`size="icon"`, ghost, 20px icon target) to delete; below the chip list, an inline add-row: `Select` (predefined category) + `Input` (free-text value) + "添加" button (`bg-primary`, disabled until both fields non-empty).
  3. Empty state (no tags yet): centered `py-8`, "暂无偏好标签" (Label 14/600) + "在下方添加第一个标签" (Label 14/400, muted-foreground) — replaces the chip list only, the add-row below is always visible regardless of chip-list state.
- Delete-tag action requires a lightweight inline confirm (not a separate `Dialog`) — reuse the existing `DropdownMenu`-style two-click affordance is overkill for a single chip; instead render the chip's delete icon-button with a `title="删除标签"` tooltip and require the destructive-confirmation copy (see Copywriting Contract) to appear as a `sonner` toast-action ("撤销" undo) rather than a blocking modal, matching this app's lightweight-destructive-action precedent (`archiveMutation`/`restoreMutation` in `training-materials.tsx` use direct mutation + toast, not a second confirm-within-confirm).

### 3. Avatar page — personalization indicator (D-13/D-14) — extends `avatar-page.tsx`'s existing header

**Structural reference:** `avatar-page.tsx`'s existing `<header>` (48px height, `border-b border-border`, currently renders the sources-panel title on the left + a ghost "登录" `Button` with `LogIn` icon on the right).

- When `useAuthStore` reports a logged-in user, the right-hand header slot swaps from the "登录" button to: username text (Label 14/400, `text-foreground`) + a small "专属模式" `Badge` (icon: `Sparkles`, 14px; `bg-primary/10 text-primary border-primary/20`; Label 14/400) — **exactly this one badge, nothing more**. No CRM content, no "matched/unmatched" indication, no preference-tag content ever renders here (D-08/D-14 hard constraint).
- Header height stays 48px (unchanged from Phase 32's contract) — the badge fits inline without increasing header height.
- Everything below the header (avatar view, transcript, input bar, sources panel) is **visually and structurally identical** whether the session is anonymous or personalized — per D-13, only the session-creation call and the injected prompt differ, never the rendered UI.

## Interaction States

### CRM Excel upload (PERS-01)

| State | Visual Treatment |
|-------|------------------|
| **Idle / no file selected** | Dropzone in default border (`border-border`), helper text "拖拽或点击上传 .xlsx 文件" (Label 14/400, muted-foreground); "上传" button disabled |
| **File selected, not yet submitted** | Dropzone shows filename + size (Body 16/400, `text-primary`), matching `training-materials.tsx`'s selected-file treatment; "上传" button enabled |
| **Uploading** | `Progress` bar + "解析中…" (Label 14/400, muted-foreground) — reuse `training-materials.tsx`'s upload-progress pattern verbatim |
| **Success (full or partial)** | Import-result card populates: 3 summary badges (success=primary tone, skipped/unmatched=weakness tone) + 2 expandable detail lists; `sonner` success toast "CRM 数据导入完成" |
| **Header validation failure (400)** | Destructive inline alert banner directly above the dropzone: "表头格式不正确" (Heading-weight text, `text-destructive`) + "请下载标准模板后重新填写并上传" (Body 16/400) — no result-summary card shown; `sonner` error toast is redundant here, use the inline banner only (avoid double-surfacing the same error) |
| **Row-level skip/unmatched (within a 200 response)** | Never rendered as an error — expandable `weakness`-toned detail rows only, each line "{{email}} — {{reason}}" (Label 14/400); this is expected, documented behavior (D-04), not a failure |

### Preference tags (PERS-03)

| State | Visual Treatment |
|-------|------------------|
| **Empty (no tags for this user)** | Centered `py-8`, "暂无偏好标签" (Label 14/600) + "在下方添加第一个标签" (Label 14/400, muted-foreground); add-row remains visible below |
| **Populated** | Wrapped `Badge` chip list, `gap-2`, each chip `{category}: {value}` + trailing `X` delete icon |
| **Adding** | Add-button shows inline pending state (reuse `Button`'s built-in `disabled` + spinner-less "添加中…" label text swap, matching `training-materials.tsx`'s upload-button pending-label pattern) |
| **Delete** | Direct mutation (no blocking dialog) + `sonner` toast with an "撤销" (undo) action button, honoring the destructive-confirmation requirement via a reversible-action pattern rather than a modal, consistent with this app's existing lightweight-destructive precedent |

### CRM match status (admin "个性化" section — read-only)

| State | Visual Treatment |
|-------|------------------|
| **Matched** | Green dot (`bg-strength`) + "已匹配 CRM 数据" (Label 14/400) + customer/company summary (Body 16/400) — **no `crm_notes`/`contact_person` shown here** |
| **Unmatched** | Muted dot (`bg-muted-foreground`) + "未匹配 CRM 数据" (Label 14/400, muted-foreground) — **neutral, never destructive/warning tone** |

### Avatar chat personalization (D-08 silent fallback — end-user-facing)

| State | Visual Treatment |
|-------|------------------|
| **User has CRM context and/or preference tags** | Chat UI renders byte-identical to a user with none — the only visible difference anywhere in the product is the header's "专属模式" badge (login-state-driven, not data-presence-driven) |
| **User has no CRM context, no tags** | Same as above — **explicitly no empty-state, no toast, no badge-state difference** may ever be keyed on "has CRM data" reaching a component the end user sees. This is a hard constraint carried over from RESEARCH.md's Pitfall 4 — any conditional render on CRM-data-presence in end-user-facing UI is a spec violation. |
