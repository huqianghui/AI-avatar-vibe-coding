# Phase 34 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase type:** i18n/translation expansion — NOT a new-visual-design phase. No new pages, no new layouts, no new color/typography tokens. This contract exists to lock down (a) how the 5-option language switcher renders, (b) how the new admin voice-map form presents, and (c) text-expansion/overflow tolerance rules so Spanish translations (typically 20-30% longer than English) never truncate or break existing layouts. All values below are the project's **existing** design tokens — reused verbatim, not redefined.

## Typography

**Unchanged from existing app tokens** (Tailwind v4 default `--text-*` scale, no overrides found in `index.css`) — **exactly 2 weights declared, matching this phase's 3 in-scope surfaces (switcher, admin voice-map form, avatar page translated text). None of the 3 surfaces renders a Display/h1-level element, so Display is intentionally excluded from the active contract below:**

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`text-base`) | 400 (`font-weight-normal`) | 1.5 |
| Label / Heading | 16-18px (`text-base`/`text-lg`) | 500 (`font-weight-medium`) | 1.5 |

**Out-of-scope reference (existing app-wide token, not part of this phase's contract):** the app also has a Display role (h1/h2 page titles, 20-24px / `text-xl`-`text-2xl` / weight 600 / line-height 1.5) defined in `frontend/src/styles/index.css:239-298`. It is documented here only for completeness of the existing design system — no page or component touched by this phase renders it, so it is explicitly **not** part of this phase's active 2-weight typography contract and must not be introduced into any of the 3 in-scope surfaces without a UI-SPEC amendment.

**Text-expansion rule (load-bearing for this phase):** Spanish strings run ~20-30% longer than their English source. Every element that renders translated copy in the 3 in-scope surfaces MUST:
1. Never use `truncate` (single-line ellipsis) on **UI chrome text** (labels, button text, switcher items, form labels). `truncate`/`line-clamp-*` on **user/content data** (e.g. `sources-panel.tsx`'s `line-clamp-2` on a citation *document title*, which is data, not UI copy) is out of scope and unaffected — do not touch it.
2. Never set a fixed `w-[Npx]` on a container that wraps translatable text without also allowing wrap (`whitespace-normal`, no `overflow-hidden` text clipping). Verified via grep: no such fixed-width+truncate combination exists in `avatar-page.tsx`, `avatar-input-bar.tsx`, or `language-switcher.tsx` today — this rule is a guardrail for new/modified code in this phase, not a fix to existing code.
3. Buttons/badges must size via padding + flex, never a hardcoded `width`.

Source: `frontend/src/styles/index.css:239-298` (base layer typography), codebase grep for `truncate|line-clamp|w-\[` across `src/components/avatar/`, `src/components/voice/`, `src/pages/avatar-page.tsx`.

## Phase-Specific Surfaces

### 1. Language Switcher — 5-option contract (`language-switcher.tsx`)

**Order (D-09, locked):** `zh-CN 🇨🇳 → en-US 🇺🇸 → es-ES 🇪🇸 → es-MX 🇲🇽 → es-US 🇺🇸` — array literal order in code must match this exactly (it is also the `supportedLngs` order required by D-10's prefix-match resolution, so the two arrays should stay visually/structurally parallel in the diff).

**Data shape per entry (extends existing `languages` array, same shape, same flag/label composition already used for zh-CN/en-US — no new props, no new component structure):**
```ts
{ code: "es-ES", labelKey: "lang.esES", flag: "\u{1F1EA}\u{1F1F8}" } // 🇪🇸
{ code: "es-MX", labelKey: "lang.esMX", flag: "\u{1F1F2}\u{1F1FD}" } // 🇲🇽
{ code: "es-US", labelKey: "lang.esUS", flag: "\u{1F1FA}\u{1F1F8}" } // 🇺🇸 — SAME emoji as en-US, intentional (D-09)
```

**Trigger button (unchanged behavior):** continues to show flag + 2-letter uppercase base-language code derived via `code.split("-")[0].toUpperCase()` — for all three es-* entries this renders `"ES"` (identical for es-ES/es-MX/es-US). This is **intentional, not a bug**: the trigger is a compact affordance (matches existing "ZH"/"EN" 2-letter convention); full disambiguation happens inside the open dropdown via the native-language label. Do not attempt to cram a region code into the trigger's 2-letter chip — that would break the established visual rhythm for a marginal gain, and the dropdown is one click away.

**Dropdown item composition (unchanged structure, extended data):** `<flag span mr-2> + {t(lang.labelKey)}` — identical DOM/class structure to today's zh-CN/en-US items. No `whitespace-nowrap` needed to add: `DropdownMenuContent` has no fixed width and auto-sizes to its longest child (`align="end"` unaffected); the longest new label ("Español (EE. UU.)", ~18 chars at 16px/400 ≈ 150-160px) comfortably fits within the dropdown's existing auto-width behavior without wrapping on any viewport ≥ 320px. No layout change required to `DropdownMenuContent`/`DropdownMenuItem` beyond adding the 3 new `<DropdownMenuItem>` entries.

**Disambiguation via label, not flag (D-09 explicit):** es-US shares its flag emoji with en-US by design — screen readers and sighted users alike rely on the rendered text label (`t(lang.labelKey)`), never the emoji alone, to distinguish the two. This is already how the component works (label text is always rendered alongside the flag, never flag-only) — no accessibility regression, no new `aria-label` needed per item.

**Selected-state highlight:** unchanged — `i18n.language === lang.code ? "font-medium text-primary" : ""`. Works identically for all 5 entries with no modification.

### 2. Admin Public Knowledge Config — voice_map 5-entry form (new admin surface, Claude's discretion per D-06/CONTEXT.md)

No admin page or admin API currently exists for `PublicKnowledgeConfig.voice_map` (confirmed absent in RESEARCH.md Open Question 1). This phase's objective requires the editing UI to exist — spec below assumes the planner adds a minimal new Card section (either a new small admin page, e.g. `src/pages/admin/public-avatar-config.tsx`, or a new Card appended to an existing config page such as `azure-config.tsx` — page **placement** is a planning decision, not a UI-SPEC concern; the **presentation pattern** below applies wherever it lands).

**Pattern: reuse the existing `Card` + `Label` + `Input` + `Button` admin-form idiom** (same idiom as `settings.tsx`'s Language Settings card and `crm-data.tsx`'s upload card — do not invent a new form pattern):

**Primary visual anchor:** the "Save Voice Settings" button is the Card's primary visual anchor, carrying the sole `--primary` accent fill on this surface; the `CardTitle` ("Voice per Language") is the secondary anchor, set in Label/Heading weight (500) with a small `--primary`-tinted icon (per the icon library row above) but no accent background — this keeps a single unambiguous action target per the 10%-accent budget.

```
Card (bg-card rounded-lg border border-border shadow-sm)
  CardHeader
    CardTitle: [Languages icon, size-5 text-primary] + "Voice per Language"
  CardContent (space-y-4)
    5x row, each: flex items-center gap-3
      - Label column: min-w-[180px] (NOT a fixed truncating width — min-width, wraps if ever needed)
          {flag} {t("common:lang.<key>")}  e.g. "🇪🇸 Español (España)"
      - Input column: flex-1 min-w-0
          value = admin override (or empty)
          placeholder = that locale's Azure default voice constant
            zh-CN → zh-CN-XiaoxiaoMultilingualNeural
            en-US → en-US-AvaNeural
            es-ES → es-ES-ElviraNeural
            es-MX → es-MX-DaliaNeural
            es-US → es-US-PalomaNeural
    Helper text (text-sm text-muted-foreground): "Leave blank to use the built-in default voice for that language."
  CardFooter or bottom-right of CardContent:
    Button (primary, disabled while pending): t("admin:voiceMap.save") -> "Save Voice Settings"
      (pending-state label may reuse existing common.json "saving" -> "Saving...")
```

**Row label width rationale (text-expansion guardrail):** `min-w-[180px]` (not `w-[Npx]` fixed, not `truncate`) — the longest label, "🇺🇸 Español (EE. UU.)", measures comfortably under 180px at 16px/400 body type; using `min-width` rather than a fixed `width` means if a future locale has an even longer native name, the column grows instead of clipping. This is the one net-new width decision in this phase and it follows the phase-wide text-expansion rule above.

**Field ordering:** same 5-locale order as the language switcher (zh-CN, en-US, es-ES, es-MX, es-US) — keep the two lists visually/conceptually parallel for admins who cross-reference them.

**Validation/empty-value semantics:** an empty Input is valid and means "use built-in default" (D-07) — never show a validation error for an empty field; only show the error-state copy (above) on a network/save failure.

### 3. Avatar Page — no layout change, translation-only verification surface

`avatar-page.tsx` requires **zero structural changes** for this phase (confirmed by code read: `useAnonymousVoiceLive(token, { locale: i18n.language })` and the `useEffect` dependency on `[i18n.language]` already rebuild the session on any language change, including the 3 new es-* values — D-11 is satisfied by existing code, not new code). The UI contract here is purely: every string rendered through `useTranslation()` on this page (and its composed children `AvatarInputBar`, `SourcesPanel`, `VoiceTranscript`, `MicPermissionDialog`) must resolve to real es-ES/es-MX/es-US text with no missing-key fallback to English (LANG-01 success criterion) — this is a content/testing concern (covered by the vitest parity test and Playwright E2E per RESEARCH.md), not a visual-design concern, and requires no changes to this UI-SPEC's layout/token contracts.

**One verified-safe existing pattern to leave untouched:** `sources-panel.tsx`'s `line-clamp-2` on `citation.title` clips *document title data* (not UI chrome copy) — out of scope, do not "fix" this as part of the text-expansion guardrail above.
