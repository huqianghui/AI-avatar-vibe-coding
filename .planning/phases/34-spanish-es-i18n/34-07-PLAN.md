<objective>
Fix the anonymous-text-chat locale-forwarding gap identified in 34-RESEARCH.md (Pitfall 3): `ChatRequest` currently carries no `locale` field, so `handle_anonymous_turn` always runs with its `locale="zh-CN"` default regardless of the UI's active language — meaning an es-ES/es-MX/es-US user typing an out-of-scope question today silently gets a Chinese refusal string. This plan adds the field end-to-end (schema -> endpoint -> service call -> frontend API client -> hook -> page) mirroring the personalized chat path, which already forwards locale correctly.

Purpose: without this fix, LANG-02's success criterion ("es-* neural voice AND text responses reflect the selected locale") is only half-true — voice negotiation (34-06) works, but the anonymous text-chat reply locale does not track the switcher. This is a locked, in-scope decision (not a deferred idea) since D-08's refusal-template completeness is meaningless if the locale never reaches the service.
Output: a 5-locale-constrained `ChatRequest.locale` field, wired end-to-end from `avatar-page.tsx`'s `i18n.language` through to `REFUSAL_TEMPLATES.get(locale, ...)`.
</objective>
