# Deferred Items — Phase 34 (Spanish es-i18n)

Items discovered during execution that are out of scope for the current plan (pre-existing issues in files not listed in `files_modified`). Logged per the executor's scope-boundary process rather than fixed inline.

## 34-03: Duplicate top-level keys in `frontend/public/locales/en-US/scoring.json`

**Found during:** Plan 34-03, Task 2 (translating `scoring.json`)

**Issue:** `en-US/scoring.json` (owned by an earlier phase, not touched by this plan) defines several top-level keys twice:
- `voiceScore` — first as a nested object (`{ title, processing, failed, retry, retrying, retryFailed, sessionRecording, audioNotSupported, dimensions: {...} }`, the "Voice Analysis" panel), then again a few lines later as a flat string `"Voice Score"`.
- `contentWeight` — first `"Content (70%)"`, then again `"Content Evaluation Weight"`.
- `voiceWeight` — first `"Voice (30%)"`, then again `"Voice Evaluation Weight"`.

Because `JSON.parse` silently keeps only the **last** occurrence of a duplicate key, the entire nested "Voice Analysis" translation sub-tree (title/processing/failed/retry/retrying/retryFailed/sessionRecording/audioNotSupported/dimensions.clarity/pace/confidence/engagement/articulation) is dead — it parses out of the object and is unreachable by any i18next lookup (`t("scoring.voiceScore.title")` would resolve to `undefined`, not the intended "Voice Analysis" string). The two `*Weight` duplicates similarly mean the "(70%)"/"(30%)" percentage-labeled variants are unreachable; only the "Evaluation Weight" labels are ever used at runtime.

**Scope decision:** `en-US/scoring.json` is not in this plan's `files_modified` list and this bug predates plan 34-03 — out of scope per the deviation-rules scope boundary (pre-existing issue in a file this plan doesn't own). Not fixed here.

**Impact on this plan's translations:** The es-ES/es-MX/es-US `scoring.json` files created in 34-03 mirror the *effective* (post-`JSON.parse`, deduplicated) key structure of `en-US/scoring.json` — i.e. `voiceScore`/`contentWeight`/`voiceWeight` are flat translated strings ("Puntuación de Voz"/"Peso de Evaluación de Contenido"/"Peso de Evaluación de Voz" for es-ES; "Puntaje de Voz"/... for es-MX/es-US), matching exactly what `locale-parity.test.ts`'s `collectLeaves()` sees when it parses `en-US/scoring.json`. This makes the parity tests pass but means the es-* locales inherit the same dead-code gap: there is no translated "Voice Analysis" panel sub-tree (clarity/pace/confidence/engagement/articulation dimension labels, retry/retrying copy, etc.) in any locale, Spanish or English, because none of it is reachable at runtime.

**Suggested resolution (future plan):** Rename the duplicate keys in `en-US/scoring.json` to restore the intended distinct sub-trees (e.g. `voiceAnalysis` for the nested panel vs. `voiceScore` for the flat "Voice Score" label; `contentWeightPct`/`voiceWeightPct` for the "(70%)"/"(30%)" display labels vs. `contentWeight`/`voiceWeight` for the "Evaluation Weight" labels), then add the corresponding translated sub-trees to all five locale files, including the two already-translated es-* files from this plan.

## 34-10: Full-suite Playwright E2E regression run — 51 pre-existing failures unrelated to Phase 34 (LANG-02 gate blocker)

**Found during:** Plan 34-10, Task 2 (full phase regression gate: `npm run test:e2e`, no file filter)

**Issue:** Running the complete E2E suite (all ~459 tests, no spec filter) produced **399 passed, 9 skipped, 51 failed**. The two new Task 1 tests (`anonymous-avatar-voice-es.spec.ts`) and every other spec file touching Phase 34's actual `files_modified` (i18n locale JSON, `language-switcher.tsx`, `avatar-page.tsx`, `voice_live_webrtc.py`, `settings.tsx`'s Voice-per-Language card, admin `voice_map` routes) are **not** among the 51 failures. Root-caused two independent, pre-existing failure clusters, neither touching any file this phase modified:

1. **`SplashScreen` (`frontend/src/components/shared/splash-screen.tsx`, introduced Phase 10, unchanged since `9c8de26`) renders a literal `<h1>{t("appName")}</h1>` ("AI Coach") for ~1.8s on every full page navigation.** Any spec that does a bare `page.locator("h1")` assertion right after `page.goto()` (no scoping) hits a Playwright *strict-mode violation* (2 elements resolve: the splash's h1 + the page's own h1) — e.g. `training.spec.ts:15`, `admin-settings.spec.ts:15`, `user-reports.spec.ts:15`, `dashboard.spec.ts:15`, `session-history.spec.ts`, `admin-scoring-rubrics.spec.ts`, `analytics.spec.ts:20`, `i18n-switching.spec.ts` (4 tests), `scenario-selection.spec.ts`, `admin-training-materials.spec.ts`, `admin-users.spec.ts`, `admin-azure-config.spec.ts`, `coaching-session.spec.ts`, `seven-modes.spec.ts`, `navigation.spec.ts` deep-link tests, `health.spec.ts`. Confirmed **deterministic, not load/flake-dependent**: reproduced identically in isolated re-runs of 3-5 files at a time, and *still failed on all 3 attempts* with `CI=true` (2 built-in Playwright retries) — Playwright's strict-mode-violation error is not part of the auto-retry-until-match polling loop for `toBeVisible()`, so waiting longer never resolves it. This is a genuine, long-standing bug (unscoped `h1` locators colliding with the global splash overlay) that predates Phase 34 by ~4 months and is unrelated to any Spanish-i18n change.
2. **Independent timeout/element-not-found failures in legacy pages Phase 34 never touches**: `training-session.spec.ts` (chat input `getByPlaceholder` timeout), `training-start-session.spec.ts` (`waitForResponse` timeout, avatar-preview visibility), `voice-live-proxy.spec.ts` (4 failures — real Azure Voice Live WS connection timeouts and a missing "Continue"/re-sync button, all against real backend chains, not mocked), `admin-hcp-profiles.spec.ts`, `admin-skill-editor.spec.ts`, `admin-skill-hub.spec.ts`, `demo-flow.spec.ts`. None of these spec files' underlying pages/components appear in any 34-01..34-10 plan's `files_modified`.

**Scope decision:** Both clusters are pre-existing bugs/flakes in files this phase's plans never listed in `files_modified` (splash-screen.tsx last touched in Phase 10; the legacy coach/admin/training pages predate Phase 34's Spanish-i18n scope entirely) — out of scope per the deviation-rules scope boundary. Not fixed here.

**Impact on this plan:** Per the plan's explicit closing-gate instruction ("mark LANG-02 complete **only if** the full regression gate, E2E included, is entirely green; otherwise leave LANG-02 open and report"), LANG-02 is **left open** in `REQUIREMENTS.md` despite Task 1's es-* voice E2E passing cleanly and every other gate command (backend ruff/pytest, frontend tsc/vitest/build) being fully green. See `34-10-SUMMARY.md` for the full gate breakdown.

**Suggested resolution (future plan):** (a) Scope every generic `page.locator("h1")` assertion in the 15 affected spec files to the page's main content region (e.g. `page.getByRole("main").locator("h1")` or a `data-testid` on the page-level heading) to stop colliding with the splash overlay's `h1`; alternatively, remove the `<h1>` semantic from `SplashScreen` (use a `<div role="img" aria-label="...">`-style non-heading element, since it's a decorative loading splash, not page content) — likely the smaller, safer fix. (b) Investigate `voice-live-proxy.spec.ts`'s real-Azure-Voice-Live-connection timeouts and `training-session.spec.ts`/`training-start-session.spec.ts`'s input/response timeouts separately — these look environment/timing related (real Azure calls, no mocking) rather than the splash-screen issue, and were not deeply root-caused given this plan's scope boundary.
