Research Pattern 2 (event-signature shim, exact shape confirmed against 40-RESEARCH.md):
```tsx
function Select({ value, onValueChange, children }: SelectProps) {
  const handleOptionSelect = (_ev: SelectionEvents, data: OptionOnSelectData) => {
    onValueChange?.(data.optionValue ?? "");
  };
  return (
    <Dropdown
      value={/* derive display text for the currently-selected value from children */}
      selectedOptions={value ? [value] : []}
      onOptionSelect={handleOptionSelect}
    >
      {children}
    </Dropdown>
  );
}
```
Deriving the display text: since `SelectItem`'s children are React-composition (arbitrary JSX, not a plain string prop), the adapter must resolve the display TEXT for the current `value` by inspecting the matching `SelectItem`'s children at render time (e.g. via `React.Children.forEach` over `SelectContent`'s children to find the `SelectItem` whose `value` prop matches, then extract its text content) — this is a genuine children-parsing problem similar in spirit to Avatar's Phase 39 LEAF-06 pattern (children-composition API -> flat-prop API), cited as the most directly relevant precedent. Verify exact approach empirically (probe-first, per Phase 39 discipline) rather than assuming `React.Children` traversal will trivially work — SelectItem's children could themselves be nested JSX requiring `ReactDOMServer` text extraction or a simpler convention (e.g. requiring SelectItem's children to resolve to renderable text via a ref-based DOM text read in a `useEffect`, matching how the ORIGINAL Radix Select likely displays the selected item's rendered content in its trigger, not a separately-tracked plain string) — read the ORIGINAL select.tsx's `SelectValue`/`SelectTrigger` implementation closely during read_first to understand exactly how display value is currently resolved, and replicate that resolution mechanism against Fluent's Dropdown `value` prop rather than inventing a new one.
