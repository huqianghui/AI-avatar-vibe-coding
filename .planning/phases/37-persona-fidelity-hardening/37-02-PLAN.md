<objective>
Make persona identity and personality actually reach the Voice Live channel: the WebRTC `session_config` for the shared anonymous-capable endpoint (`/public/avatar/webrtc/session`, used by both anonymous and logged-in sessions per D-13) gains an `avatar: {character, style}` block (PERSONA-05) and an `instructions` field carrying the sanitized persona prompt fragment, merged with CRM/preference context for logged-in callers (PERSONA-06).

Purpose: Phase 36 wired persona prompt fragments into text-chat only; the voice channel — the primary interaction surface — has never reflected persona identity or personality until now. This plan closes that gap using exclusively proven, already-tested primitives (D-37-2's mandate).

D-37-2 ("logged-in path merges CRM/preference context") requires resolving a `user_id` on an endpoint that, per D-13/D-37-1, never receives a JWT for anonymous callers and has no existing optional-auth mechanism. This plan adds a NEW, minimal, additive-only dependency (`get_optional_current_user`) rather than relaxing D-13 or inventing a new endpoint — documented explicitly below and in the threat model, not a silent scope change.

Output: `avatar`+`instructions` keys in `session_config`, `character`/`style` on `WebRTCSessionResponse`, `get_optional_current_user` dependency, a live-Azure smoke-test checkpoint for the two behavioral open questions RESEARCH.md could not resolve statically.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Anonymous client -> `/public/avatar/webrtc/session` | Untrusted, `X-Anon-Session` required (unchanged); `Authorization` header now OPTIONALLY read but never required |
| Optionally-authenticated client -> same endpoint | A caller who supplies BOTH `X-Anon-Session` AND a valid `Authorization: Bearer` -- gets persona+CRM resolution scoped to their own JWT-derived `user_id`, never a client-supplied one |
| `persona.prompt_fragment` (admin-authored) -> Voice Live `instructions` | NEW attack surface this phase opens -- first time this field reaches Voice Live directly as a system-prompt-equivalent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-04 | Elevation of Privilege | `get_optional_current_user` silently swallowing an invalid/expired token instead of raising | accept | Deliberate: this endpoint's core contract (D-13) is that a JWT is never required; a malformed/expired token degrading to "anonymous" is the correct fallback, not a privilege escalation -- no code path grants elevated access from a bad token, it only ever grants LESS (falls back to default persona, no CRM) |
| T-37-05 | Tampering / Elevation of Privilege | `persona.prompt_fragment` reaching `instructions` (voice channel's first exposure to this field) | mitigate | Two-gate sanitization reused unchanged: gate 1 (`sanitize_free_text_with_pii` at admin-save, from 37-01/36-01) + gate 2 (same function, re-applied at injection time in this plan) -- no new sanitizer per D-37-2 |
| T-37-06 | Information Disclosure | CRM/preference content leaking into an anonymous session's `instructions` | mitigate | `crm_context` is only ever computed when `current_user` was genuinely resolved from a valid JWT (`if current_user else None`) -- an anonymous caller's `current_user` is always `None`, so `build_personalization_context` is never even called |
| T-37-07 | Information Disclosure | `requested_persona_id` enumeration (pre-existing, must not regress) | accept (already mitigated upstream) | `resolve_active_persona`'s existing silent-fallback-to-default behavior for disabled/unknown ids is untouched by this plan -- no new distinguishable error introduced |
</threat_model>
