```typescript
/**
 * Voice Live WebRTC hook — direct browser-to-Azure audio via RTCPeerConnection.
 *
 * Architecture (from Azure Voice Live WebRTC docs):
 *   1. WebSocket signaling channel (to Azure /voice-live/realtime/calls endpoint)
 *      — SDP exchange, session.update, function calls
 *   2. WebRTC RTP media tracks (bidirectional audio: mic -> Azure, Azure TTS -> speaker)
 *   3. WebRTC data channel "voice-live-events"
 *      — VAD events, transcripts, response lifecycle
 *
 * Key differences from useVoiceLive (WebSocket proxy):
 *   - Audio never touches the backend (lower latency)
 *   - Backend only provides auth token + signaling URL (token broker role)
 *   - Mic audio captured via getUserMedia and fed to RTCPeerConnection addTrack
 *   - Remote audio played via <audio> element with srcObject from ontrack event
 *   - Non-audio events (transcripts, VAD) arrive on RTCDataChannel, not WebSocket
 *
 * Per D-08: No auto-fallback. If WebRTC fails, shows clear error.
 * Per D-09: 3-attempt reconnection on mid-session disconnects with exponential backoff.
 */
export function useVoiceLiveWebRTC(options: VoiceLiveOptions): VoiceLiveControls
```

Implementation requirements:
- **State:** connectionState, audioState, isMuted — same as useVoiceLive
- **Refs:** pcRef (RTCPeerConnection), signalingWsRef (WebSocket), dataChannelRef (RTCDataChannel), micStreamRef (MediaStream), remoteAudioRef (HTMLAudioElement), reconnectAttemptRef (number), reconnectTimerRef, intentionalCloseRef, lastConnectArgsRef
- **connect function:**
  1. Call `fetchWebRTCSession(hcpProfileId, vlInstanceId)` to get signaling URL + bearer token
  2. `navigator.mediaDevices.getUserMedia({ audio: true })` for mic access
  3. Create `new RTCPeerConnection()` (no ICE servers needed — Azure handles TURN)
  4. `stream.getTracks().forEach(track => pc.addTrack(track, stream))` — bidirectional audio (sendrecv)
  5. Create data channel BEFORE createOffer: `pc.createDataChannel('voice-live-events')`
  6. Set up `dc.onmessage` handler to parse JSON and dispatch to appropriate callback (onTranscript for `response.audio_transcript.delta/done`, `input_audio_buffer.speech_started/stopped` for audioState)
  7. Set up `pc.ontrack` for remote audio playback: create `<audio>` element, set srcObject, autoplay
  8. Create SDP offer: `pc.createOffer()` then `pc.setLocalDescription(offer)`
  9. Wait for ICE gathering complete: listen for `pc.onicegatheringstatechange` or timeout after 5 seconds
  10. Open signaling WebSocket to Azure: `new WebSocket(session.signaling_url)` with `api-key` as subprotocol if auth_type is api-key, OR append `?api-key={token}` as query parameter for bearer tokens use `Authorization` header approach — since browser WebSocket cannot set headers, use the azure approach: append the API key as query parameter `&api-key={auth_token}` to the signaling URL
  11. On ws.onopen: send `{ type: "rtc.call.sdp.create", sdp_offer: pc.localDescription.sdp }`
  12. Wait for `rtc.call.sdp.created` response with sdp_answer
  13. `pc.setRemoteDescription({ type: "answer", sdp: answer.sdp_answer })`
  14. Send `{ type: "session.update", session: session.session_config }` via signaling WS
  15. Set connectionState to "connected"
  16. Return `{ avatarEnabled: false, model: session.model, iceServers: [] }` (avatarEnabled always false per Azure limitation)

- **disconnect function:** Close pc, close signaling WS, stop mic tracks, remove audio element, set state to "disconnected"

- **toggleMute:** Enable/disable mic tracks via `micStreamRef.current.getTracks().forEach(t => t.enabled = !t.enabled)`

- **sendTextMessage:** Send `{ type: "conversation.item.create", item: { type: "message", role: "user", content: [{ type: "input_text", text }] } }` via signaling WebSocket, then send `{ type: "response.create" }`

- **sendAudio:** No-op for WebRTC (audio goes via RTP track, not manual sending)

- **send:** Forward raw message to signaling WebSocket as JSON

- **reconnection logic (per D-09):** On `pc.onconnectionstatechange` detecting "disconnected" or "failed", attempt reconnect up to 3 times with delays [1000, 2000, 4000]ms. If all attempts fail, set connectionState to "error" and call `options.onError(new Error("WebRTC connection failed after 3 attempts"))`

- **Data channel message handling:** Parse JSON messages and handle:
  - `input_audio_buffer.speech_started` → set audioState to "listening"
  - `input_audio_buffer.speech_stopped` → set audioState to "idle"
  - `response.audio_transcript.delta` → accumulate transcript, call onTranscript with isFinal=false
  - `response.audio_transcript.done` → call onTranscript with isFinal=true
  - `response.created` → set audioState to "speaking"
  - `response.done` → set audioState to "idle"

- **avatarSdpCallbackRef:** Set to useRef(null) — not used for WebRTC audio transport but needed for interface compatibility

- **Cleanup:** On unmount, disconnect and clean up all resources

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> Azure signaling WS | Bearer token passed as query parameter on WSS (encrypted by TLS) |
| browser -> Azure RTP | Audio media encrypted by DTLS-SRTP (WebRTC standard) |
| browser -> backend /webrtc/session | JWT auth for token brokering |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-06 | Information Disclosure | Bearer token in URL query param | accept | WSS encrypts entire URL including query params; token is short-lived (10 min STS); this is Azure's documented auth pattern for browser WebSocket |
| T-26-07 | Denial of Service | getUserMedia permission denial | mitigate | Catch NotAllowedError, set connectionState to "error", call onError with descriptive message |
| T-26-08 | Spoofing | Signaling URL tampering by MITM | mitigate | URL is served over HTTPS from backend; signaling channel uses WSS (TLS); no user input in URL construction |
| T-26-09 | Information Disclosure | ICE candidate IP leakage | accept | Standard WebRTC behavior; no TURN servers needed (Azure endpoint); browser security model applies |
</threat_model>
